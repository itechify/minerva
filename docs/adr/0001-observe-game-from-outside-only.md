# Observe the game from outside only

Minerva must not be seen as interacting with the MapleStory client, because third-party interaction can breach the terms of service and get the player's account banned. So it only reads pixels through the operating system's ordinary screen-capture APIs, and it only draws in its own separate windows. It never reads or writes the game's memory or files at runtime, never injects code or hooks the renderer, and never sends input to the game.

The overlay panel is always clickable: wherever it shows, a click on it lands on Minerva and the game doesn't see it, just as with any other window in front of the game. The player drags the panel by its header and clicks its buttons at any time. A click never takes the keyboard from the game, though: the overlay is a no-activate window (`WS_EX_NOACTIVATE`), so Windows leaves the game as the active window. While there is no game window to show the panel over, or another app is in front, the overlay draws nothing and lets every click through. The Grind Tracker's window is the same kind of window: always clickable, no-activate, on top of everything while it shows, and hidden while there is no game window or another app is in front. So is the Item Lookup alert's (ADR 0007), at the top centre of the game window for a few seconds after an Item Lookup, except that it lets every click through to the game unless it lists items to pick from. So is the Item Card's (ADR 0010), at the pointer until the player closes it: it takes the clicks on itself while a card shows, and lets every click through while none does. A click elsewhere goes to the game, and Minerva never hears of it, so the card doesn't close on one. Until ADR 0021, a region-marking window took the mouse over the game while the player dragged a box around the minimap title at setup; the title is found by itself now, and there is no such window.

The search view is the only time the overlay takes the keyboard. The search hotkey or a click on one of the panel's 🔍 buttons opens it: the overlay becomes focusable and comes to the front with `SetForegroundWindow` on our own window, right after that hotkey or click, like any app window the player switches to, so their typing and keys go to it. Pressing the hotkey again with the view open brings the overlay back in front the same way. Picking a map, the back arrow, Esc, or switching to the game or another app closes the view. The overlay is then no-activate again; if it still has the foreground, it hides and shows itself again without activating, so Windows gives focus back to the window below it, the game. Nothing is sent to the game at any point. The Settings window, a window of its own, takes the keyboard the same way: as it opens and right after a click on one of its Change buttons or its Deal Margin field. Switching to the game gives it back, and the window stays open. So does the Item Card's market price field (ADR 0010), right after the player's click on the card's price, until Enter, Esc or a click elsewhere closes it.

Keyboard input comes only through global hotkeys registered with the operating system (`RegisterHotKey` on Windows): the system tells us when the player presses one of our combinations. There are no low-level keyboard hooks (`WH_KEYBOARD_LL`) and no polling of key state (`GetAsyncKeyState`). A registered combination reaches no other window, so the hotkeys are registered only while the game or one of our windows is in front, and released as soon as another app is. We tell which window is in front with `GetForegroundWindow`, polled as for the overlay windows' visibility (below), so other apps keep their own shortcuts. The defaults are Ctrl+Shift+letter. Win+Alt+letter was tried first, to stay clear of what players bind in the game, but Windows and other apps already hold many of those letters (Win+Alt+F was taken on the owner's machine). So we accept that a Ctrl+Shift combination we register is lost to the game while it is in front, and a player who binds one in the game rebinds ours in the settings file.

## Consequences

The map has to be inferred from the rendered minimap title (OCR or glyph matching) rather than read directly. Shortcuts such as reading the current map ID from process memory are permanently off the table, even though they would be more accurate.

To belong to the game rather than float over every app, the overlay windows (the panel's, the Grind Tracker's, the Item Lookup alert's and the Item Card's) show on top of everything only while the game or one of our windows is in front, and hide while another app is. We tell by polling `GetForegroundWindow`, and restack only our own windows (`SetWindowPos` with no activation): topmost while they show, the bottom of the z-order once another app comes in front. Making the overlay an owned or child window of the game (`GWLP_HWNDPARENT`, `SetParent`) would tie it to the game for free, but it is ruled out: a cross-process owner or parent link attaches our input queue to the game's, which is interaction with the game client. Window-event hooks (`SetWinEventHook`) to hear of foreground changes are avoided for the same reason.

**Amended 2026-10-09 (PR #50).** Until then the overlay was never topmost: it was kept just above the game in the z-order, so that it would never cover another app, and an app brought in front of the game covered the overlay too. The overlay windows are now topmost while they show, and hide as soon as another app is in front. They still never cover another app, so that reason for keeping out of the topmost band no longer applies. The decision itself stands: no owner or parent link to the game, no hooks, and no messages or input to it; only our own windows are restacked.

Our windows are not hidden from screen capture, so the panel shows in the player's screenshots and streams. Our own capture of the Minimap Title where it was found (ADR 0021; and of the Status Bar, its Character and EXP figures) would then read the panel if it covered them, so the core never places the panel there: inside the game window it moves clear of every captured region, whether at its default spot or where the player dragged it. The Grind Tracker's window, the Item Lookup alert and the Item Card move clear of them the same way. The Item Card may cover the Item Tooltip the next press reads, so the shell moves it off the screen before that capture, and the core puts it back.
